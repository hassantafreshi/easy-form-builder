# ADDON_COMPATIBILITY.md — Add-on Integration Map (evidence-based)

All add-ons live under `vendor/` (a separately-versioned nested git repo, remote
`vendores-efb`, currently 1 commit ahead of its own origin with 2 modified zip files in the
working tree — **verify the checked-out vendor state before trusting "current" behavior
conclusions**, since it may not match what a fresh checkout would have). No
`includes/addons/` directory exists.

**Confirmed dead / unreferenced**: `vendor/import-export/` (docs only, no PHP), `vendor/_logic/`
and `vendor/v4.1 backup/`, `vendor/v4.1.2/` (stale byte-identical copies of the conditional
logic validator — the memory note "3 PHP copies" is precise; only
`vendor/logic/logic/class-Emsfb-logic-validator.php` is actually `require_once`'d,
`includes/class-Emsfb.php:411`, with `vendor/logic/class-Emsfb-logic-validator.php` as a
fallback path). Do not port the dead copies into the extraction.

## Two independent gating layers (inconsistent — document, do not silently unify)

1. **Class-instantiation gate** (`includes/class-Emsfb.php:298-472`): each add-on's PHP
   bootstrap loads only if `Adn<Code> == 1` (or `>=1`) **and**
   `emsfb_is_addon_compatible_efb('Adn<Code>')` passes. Consistent across all add-ons.
2. **Builder-screen UI gate** (inside `includes/admin/assets/js/val-efb.js`'s `formSet` panel
   and `admin-efb.js`'s palette rendering): **inconsistent**. Telegram and Conditional Logic
   sections are correctly wrapped in `efb_var.addons.Adn*` checks; the **SMS section and the
   Offline-Forms toggle in the exact same panel are not** — they always render in the DOM even
   when the add-on is off (though their server-side effects stay gated). A future redesign
   should decide whether to make this uniform, but the extraction itself must preserve the
   asymmetry, not silently "fix" it.
3. `fields_efb` (`val-efb.js:23-79`) is the single source of truth for the field palette; the
   same `Adn*` per-entry gating logic is **duplicated** between `admin-efb.js:2179-2199` and
   `val-efb.js:2179-2198` — a divergence risk (two places to keep in sync) worth flagging.

## Shared coupling surface for extension UIs

`#settingModalEfb` / `#settingModalEfb-title` / `#settingModalEfb-icon` / `#settingModalEfb-body`
(markup defined `includes/admin/class-Emsfb-create.php:181-191`) plus the global
`state_modal_show_efb()` function is the reusable "add-on settings dialog" contract. Currently
only Conditional Logic uses it, but it's the template the reserved-but-unimplemented flags
(`AdnWHS` webhook, `AdnBEF` booking, `AdnSE` search entry, etc. — see
`get_all_addon_keys_efb()`, `includes/functions.php:2992`) would likely reuse. **A future UI
replacing `ui-legacy` must preserve this modal-shell contract, or provide an equivalent hook,
or every add-on with a settings UI breaks.**

## No add-on registers its own core-save-equivalent hook

Confirmed: no add-on hooks a generic "form saved" event. Each either (a) piggybacks the core
save handler inline (SMS only — a special case, not a pattern), (b) fires its own hooks from
the public *submission* pipeline (Telegram, Conditional Logic, Google Sheet — not the
builder's save/update at all), or (c) has no server-side save/load coupling (Human Shield,
Stripe/PayPal/PersiaPay beyond their own REST checkout routes). See AJAX_API.md "No
`emsfb_form_saved`-style hook" for the corresponding statement from the backend side.

## Reserved-but-unimplemented flags (no `vendor/` folder exists)

`AdnATC` (tracking code), `AdnCPF`, `AdnESZ`, `AdnSE` (search entry), `AdnWHS` (webhook),
`AdnWSP`, `AdnPLF`, `AdnMSF`, `AdnBEF` (booking) — from `get_all_addon_keys_efb()`
(`includes/functions.php:2992`). Note: webhook/notification/confirmation "rules" already exist
today as **scopes inside the Conditional Logic add-on's rule engine**, not as a separate
`AdnWHS` add-on — don't conflate the flag name with unbuilt functionality.
