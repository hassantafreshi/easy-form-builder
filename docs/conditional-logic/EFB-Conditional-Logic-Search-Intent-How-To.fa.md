# راهنمای تیتروار کاندیشنال لاجیک Easy Form Builder بر اساس نیازهای سرچ کاربران

این فایل برای نویسنده محتوا و مستندساز آماده شده است. هر تیتر شبیه عبارتی نوشته شده که کاربر ممکن است در گوگل سرچ کند، و زیر هر تیتر توضیح داده شده که ادمین وردپرس در Easy Form Builder چطور همان رفتار را به صورت بصری بسازد.

> نکته: این راهنما فقط قابلیت‌های قابل ساخت در UI فعلی کاندیشنال لاجیک را توضیح می‌دهد. قابلیت‌های AI مثل ساخت rule با پرامپت، optimizer یا simulator فعلاً باید به عنوان نقشه راه و قابلیت آینده معرفی شوند.

---

## 1. چطور یک فیلد را بر اساس پاسخ کاربر نمایش دهیم؟

کاربر معمولاً دنبال این است که مثلاً اگر گزینه «شرکتی» انتخاب شد، فیلد «نام شرکت» یا «شماره مالیاتی» نمایش داده شود. برای ساخت این حالت، ادمین ابتدا فیلد شرطی و فیلدی که قرار است نمایش داده شود را در فرم می‌سازد. سپس وارد Conditional Logic می‌شود، در تب Fields روی Add کلیک می‌کند و یک rule جدید می‌سازد.

در بخش IF، فیلد مبنا را انتخاب می‌کند؛ مثلاً Customer Type. سپس operator را روی is قرار می‌دهد و مقدار Business را انتخاب می‌کند. در بخش THEN، action را روی Show Field می‌گذارد و target را فیلدی انتخاب می‌کند که باید ظاهر شود؛ مثلاً Company Name یا VAT Number. بعد از Save، بهتر است با Test Mode مقدار Business را تست کند و ببیند rule با وضعیت Matched اجرا می‌شود.

## 2. چطور یک فیلد را وقتی کاربر گزینه خاصی انتخاب کرد مخفی کنیم؟

برای مخفی کردن فیلد، ادمین همان مسیر ساخت rule را طی می‌کند اما در بخش THEN اکشن Hide Field را انتخاب می‌کند. مثال رایج این است که اگر کاربر نوع درخواست را Personal انتخاب کرد، فیلدهای Company Name، Tax ID یا Business Address مخفی شوند.

اگر چند فیلد باید مخفی شوند، ادمین می‌تواند در همان rule چند action اضافه کند و برای هر action یک target جداگانه انتخاب کند. فیلدهای مخفی‌شده در ارسال فرم ignored می‌شوند، بنابراین اگر قبلاً required بوده‌اند یا کاربر در مسیر قبلی مقداری وارد کرده باشد، نباید مانع ارسال فرم شوند.

## 3. چطور یک فیلد را فقط در شرایط خاص required کنیم؟

برای required کردن شرطی، ادمین باید rule را در تب Fields بسازد. در بخش IF شرط را تعریف می‌کند؛ مثلاً اگر Request Type برابر Support باشد. سپس در بخش THEN اکشن Set Required را انتخاب می‌کند و فیلدی مثل Activation Code را target قرار می‌دهد.

این حالت برای فرم‌هایی مناسب است که یک فیلد فقط در یک مسیر ضروری است. مثال‌ها: شماره سفارش فقط برای درخواست پشتیبانی، نام شرکت فقط برای مشتریان تجاری، یا شماره پاسپورت فقط برای نوع سفر بین‌المللی. در Test Mode باید هر دو مسیر تست شود: یک بار وقتی rule match می‌شود و فیلد required است، و یک بار وقتی match نمی‌شود.

## 4. چطور یک فیلد required را در بعضی مسیرها optional کنیم؟

اگر یک فیلد در فرم به صورت پیش‌فرض required است اما در بعضی پاسخ‌ها نباید اجباری باشد، ادمین می‌تواند از Set Optional استفاده کند. ابتدا rule را در تب Fields می‌سازد، شرط را در IF تعیین می‌کند، سپس در THEN اکشن Set Optional را انتخاب می‌کند و فیلد مورد نظر را target می‌کند.

این کاربرد برای فرم‌های چندمسیره مهم است. مثلاً فیلد Company Registration Number برای شرکت‌ها required است، اما اگر کاربر نوع حساب را Individual انتخاب کرد، همان فیلد optional یا حتی hidden می‌شود. اگر فیلد هم optional و هم hidden شود، باید مطمئن شد ruleها با Priority درست اجرا می‌شوند.

## 5. چطور یک فیلد را بر اساس شرط غیرفعال کنیم؟

برای قفل کردن یک فیلد بدون مخفی کردن آن، ادمین از Disable Field استفاده می‌کند. در تب Fields یک rule می‌سازد، در IF شرط را مشخص می‌کند و در THEN اکشن Disable Field را روی فیلد target قرار می‌دهد.

این کار وقتی مناسب است که کاربر باید مقدار را ببیند اما نباید تغییر دهد؛ مثل فیلد قیمت، کد کاربری، مقدار پرشده از dataset، یا گزینه‌ای که بعد از انتخاب یک مسیر نباید ویرایش شود. اگر لازم است بعداً دوباره قابل ویرایش شود، باید rule دیگری با Enable Field برای مسیر مقابل ساخته شود.

## 6. چطور یک فیلد غیرفعال را دوباره فعال کنیم؟

برای فعال کردن دوباره فیلد، ادمین یک rule با اکشن Enable Field می‌سازد. مثال: اگر کاربر گزینه Manual Entry را انتخاب کرد، فیلد آدرس که قبلاً به صورت خودکار یا disabled بود دوباره فعال شود.

بهتر است برای حالت‌های enable/disable، شرط‌ها واضح و غیرمتعارض باشند. اگر چند rule روی یک فیلد اثر می‌گذارند، ادمین باید Priority را تنظیم کند تا rule نهایی همان رفتاری را بسازد که انتظار دارد.

## 7. چطور در فرم چندمرحله‌ای یک مرحله را مخفی کنیم؟

برای مخفی کردن یک مرحله کامل، ادمین باید فرم را به صورت multi-step ساخته باشد. سپس وارد Conditional Logic می‌شود، در تب Fields یک rule اضافه می‌کند، شرط مسیر را در IF می‌سازد و در THEN اکشن Hide Step را انتخاب می‌کند. target در این حالت از لیست stepها انتخاب می‌شود، نه فیلدها.

مثال رایج: اگر Customer Type برابر Personal باشد، مرحله Company Information مخفی شود. وقتی step مخفی می‌شود، فیلدهای داخل آن نیز ignored می‌شوند و required بودن آن‌ها نباید کاربر را متوقف کند. این رفتار باید با مسیرهای Next و Previous تست شود.

## 8. چطور یک مرحله را فقط برای بعضی کاربران نمایش دهیم؟

برای نمایش شرطی یک مرحله، ادمین از Show Step استفاده می‌کند. این حالت وقتی کاربرد دارد که یک مرحله باید در ابتدا پنهان باشد و فقط در مسیر مشخص باز شود؛ مثلاً مرحله Payment Details فقط وقتی نمایش داده شود که کاربر پلن پولی را انتخاب کرده است.

در بخش IF باید فیلدی انتخاب شود که مسیر کاربر را تعیین می‌کند؛ مثلاً Plan is Pro. سپس در THEN اکشن Show Step و target همان مرحله انتخاب می‌شود. اگر چند مرحله با هم وابسته‌اند، هر مرحله باید rule یا action مناسب خودش را داشته باشد.

## 9. چطور کاربر را بعد از یک پاسخ مستقیماً به مرحله خاص ببریم؟

برای پرش مستقیم در فرم چندمرحله‌ای، ادمین از Jump to Step استفاده می‌کند. در IF شرط را می‌سازد؛ مثلاً اگر Issue Type برابر Technical باشد. در THEN اکشن Jump to Step را انتخاب می‌کند و target را مرحله Troubleshooting قرار می‌دهد.

این قابلیت با Hide Step فرق دارد، چون فقط مرحله‌ای را پنهان نمی‌کند؛ بلکه کاربر را همان لحظه به مقصد منتقل می‌کند. بعد از ساخت، باید تست شود که دکمه Previous، نوار پیشرفت و validation مرحله مقصد درست کار می‌کنند.

## 10. چطور داخل فرم پیام راهنما یا هشدار شرطی نشان دهیم؟

برای نمایش پیام داخل فرم، ادمین از Show Message استفاده می‌کند. در IF شرط را تعیین می‌کند؛ مثلاً اگر Budget کمتر از 1000 بود. در THEN اکشن Show Message را انتخاب می‌کند، فیلد target را مشخص می‌کند و متن پیام را می‌نویسد.

این پیام کنار فیلد target نمایش داده می‌شود و برای توضیح‌های لحظه‌ای مناسب است. مثال‌ها: «حداقل بودجه پروژه 1000 دلار است»، «برای درخواست پشتیبانی، کد فعال‌سازی را وارد کنید»، یا «این گزینه فقط برای کاربران تجاری فعال است.»

## 11. چطور یک فیلد را به صورت خودکار مقداردهی کنیم؟

برای مقداردهی خودکار، ادمین از Set Value استفاده می‌کند. در IF مشخص می‌کند چه زمانی مقدار باید تنظیم شود، سپس در THEN اکشن Set Value را انتخاب می‌کند، فیلد target را تعیین می‌کند و مقدار ثابت را وارد می‌کند.

مثال: اگر Department برابر Sales بود، فیلد Hidden Route مقدار sales بگیرد. یا اگر Plan برابر Enterprise بود، فیلد Lead Priority مقدار high بگیرد. اگر Auto-Populate/Dataset فعال باشد، ادمین می‌تواند به جای مقدار ثابت، ستون dataset را به عنوان منبع مقدار انتخاب کند.

## 12. چطور مقدار یک فیلد را هنگام تغییر مسیر کاربر پاک کنیم؟

برای پاک کردن مقدار قبلی، ادمین از Clear Value استفاده می‌کند. این اکشن وقتی لازم است که کاربر قبلاً یک مسیر را انتخاب کرده و مقداری وارد کرده، اما بعداً مسیرش را تغییر داده است و مقدار قبلی دیگر نباید در submission باقی بماند.

مثال: اگر کاربر از Business به Personal تغییر مسیر داد، مقدار VAT Number یا Company Name پاک شود. در IF شرط مسیر جدید را می‌سازید و در THEN اکشن Clear Value را برای فیلدهای مرتبط اضافه می‌کنید.

## 13. چطور شرط AND بسازیم؟

برای ساخت AND، ادمین در بخش IF چند شرط اضافه می‌کند و connector بین آن‌ها را روی AND قرار می‌دهد. مثال: Country is Canada AND Customer Type is Business. این یعنی rule فقط وقتی اجرا می‌شود که هر دو شرط هم‌زمان برقرار باشند.

بعد از ساخت شرط‌های AND، در THEN رفتار مورد نظر را انتخاب می‌کند؛ مثلاً Show Field برای Province یا Set Required برای VAT Number. اگر یکی از شرط‌ها برقرار نباشد، rule نباید match شود.

## 14. چطور شرط OR بسازیم؟

برای ساخت OR، ادمین چند شرط در بخش IF اضافه می‌کند و connector بین آن‌ها را روی OR قرار می‌دهد. مثال: Department is Sales OR Department is Support. این یعنی اگر یکی از شرط‌ها برقرار باشد، action اجرا می‌شود.

OR برای مسیرهایی مناسب است که چند پاسخ مختلف باید یک رفتار مشترک داشته باشند. مثلاً اگر نوع درخواست Sales یا Partnership بود، فیلد Budget نمایش داده شود.

## 15. چطور شرط‌های پیچیده با گروه‌بندی بسازیم؟

برای شرط‌های پیچیده، ادمین از Add Group استفاده می‌کند. داخل گروه می‌تواند چند شرط با AND/OR بسازد و سپس خود گروه را با شرط‌های بیرونی ترکیب کند. مثال: (Plan is Premium AND Budget greater than 5000) OR Coupon Code is FORCE.

گروه‌بندی برای فرم‌هایی لازم است که تصمیم‌گیری فقط با یک شرط ساده انجام نمی‌شود. نویسنده مقاله باید تأکید کند که ادمین بهتر است ruleهای پیچیده را نام‌گذاری کند و با Test Mode چند سناریو مختلف را بررسی کند.

## 16. چطور شرط عددی بسازیم؟

برای شرط عددی، ادمین باید فیلد عددی مثل Number یا Range داشته باشد. در بخش IF همان فیلد را انتخاب می‌کند و operatorهایی مثل greater than، less than، greater than or equal یا less than or equal را انتخاب می‌کند. مقدار شرط در ورودی عددی نوشته می‌شود.

مثال: اگر Budget greater than 5000 بود، فیلد Consultation Type نمایش داده شود یا notification به مدیر ارسال شود. برای عددهای حساس، بهتر است مقادیر صفر، خالی و اعشاری نیز در Test Mode بررسی شوند.

## 17. چطور شرط between یا بازه عددی بسازیم؟

برای شرط بازه‌ای، ادمین فیلد عددی را در IF انتخاب می‌کند و operator را روی between یا not between می‌گذارد. UI دو ورودی Min و Max نشان می‌دهد و ادمین بازه را وارد می‌کند.

مثال: اگر Budget between 1000 and 5000 بود، پیام مخصوص پروژه‌های متوسط نمایش داده شود. اگر Budget not between 1000 and 5000 بود، مسیر دیگری فعال شود. باید توجه کرد مقدار خالی نباید به عنوان عدد معتبر در نظر گرفته شود.

## 18. چطور شرط خالی بودن یا پر بودن فیلد بسازیم؟

برای بررسی خالی بودن، ادمین در IF فیلد را انتخاب می‌کند و operator را روی is empty یا is not empty می‌گذارد. در این حالت نیازی به وارد کردن value نیست و builder فیلد مقدار را نمایش نمی‌دهد.

مثال: اگر Referral Code is not empty بود، فیلد Discount Reason نمایش داده شود یا ایمیل جداگانه ارسال شود. اگر Upload File is empty بود، پیام راهنما نمایش داده شود.

## 19. چطور برای checkbox یا multiselect شرط بسازیم؟

برای فیلدهای checkbox و multiselect، ادمین فیلد را انتخاب می‌کند و مقدار را از optionهای همان فیلد برمی‌دارد. rule زمانی match می‌شود که گزینه مورد نظر در انتخاب‌های کاربر وجود داشته باشد.

مثال: اگر Services شامل Website Design بود، فیلد Project Pages نمایش داده شود. اگر کاربر چند سرویس انتخاب کند، هر rule می‌تواند بر اساس یکی از گزینه‌های انتخابی اجرا شود.

## 20. چطور برای فیلد Yes/No شرط بسازیم؟

برای Yes/No، ادمین فیلد را در IF انتخاب می‌کند و مقدار yes یا no را انتخاب می‌کند. مثال: اگر Have Website برابر yes بود، فیلد Website URL نمایش داده شود؛ اگر no بود، فیلد Brand Assets نمایش داده شود.

این نوع شرط برای فرم‌های ساده و سریع بسیار مناسب است، چون کاربر فقط یک انتخاب دودویی انجام می‌دهد و فرم بر اساس همان انتخاب تغییر می‌کند.

## 21. چطور برای پرداخت موفق یا ناموفق شرط بسازیم؟

اگر فرم فیلد پرداخت مثل Stripe یا PayPal دارد، ادمین می‌تواند شرط پرداخت بسازد. در IF فیلد پرداخت را انتخاب می‌کند و operatorهایی مثل is paid یا is not paid را به کار می‌برد. برای این دو operator نیازی به مقدار نیست.

مثال: اگر Payment is paid بود، confirmation مخصوص پرداخت موفق نمایش داده شود یا webhook به سیستم سفارش ارسال شود. اگر Payment is not paid بود، پیام راهنما یا مسیر دیگری فعال شود.

## 22. چطور براساس مبلغ پرداخت شرط بسازیم؟

برای شرط مبلغ، ادمین فیلد پرداخت را انتخاب می‌کند و operatorهایی مثل amount equals، amount greater than یا amount less than را انتخاب می‌کند. سپس مبلغ مورد نظر را وارد می‌کند.

مثال: اگر amount greater than 1000 بود، notification به مدیر فروش ارسال شود. این نوع rule برای فرم‌های سفارش، ثبت‌نام پولی یا درخواست خدمات حرفه‌ای کاربرد دارد.

## 23. چطور ایمیل را براساس پاسخ کاربر به تیم مناسب بفرستیم؟

برای ارسال ایمیل شرطی، ادمین وارد تب Notifications می‌شود، Add می‌زند و در IF شرط مسیر را می‌سازد؛ مثلاً Department is Sales. سپس در تنظیمات همان rule ایمیل گیرنده، subject و template را وارد می‌کند.

برای routing کامل، می‌توان چند notification rule ساخت: یکی برای Sales، یکی برای Support و یکی برای Billing. هر rule فقط وقتی اجرا می‌شود که شرط خودش match شود.

## 24. چطور برای leadهای مهم ایمیل جداگانه ارسال کنیم؟

ادمین در تب Notifications یک rule می‌سازد که IF آن مثلاً Budget greater than 5000 یا Plan is Enterprise باشد. سپس recipient را ایمیل مدیر یا تیم فروش ویژه می‌گذارد و subject را متناسب با lead مهم تنظیم می‌کند.

این کار باعث می‌شود همه submissionها یکسان پردازش نشوند. کاربران ارزشمندتر یا درخواست‌های حساس می‌توانند به تیم جداگانه، ایمیل متفاوت یا مسیر پیگیری سریع‌تر ارسال شوند.

## 25. چطور بعد از ارسال فرم پیام تشکر متفاوت نشان دهیم؟

برای پیام تشکر شرطی، ادمین وارد تب Confirmation می‌شود. در IF شرط را می‌سازد؛ مثلاً Request Type is Support. سپس action را روی message می‌گذارد و متن پیام را وارد می‌کند.

در همین بخش می‌تواند done title، icon، tracking code label و رنگ‌های پیام را تنظیم کند. مثال: درخواست پشتیبانی پیام «تیم پشتیبانی به زودی پاسخ می‌دهد» ببیند، اما درخواست فروش پیام «مشاور فروش با شما تماس می‌گیرد» دریافت کند.

## 26. چطور بعد از ارسال فرم کاربر را به صفحه خاص منتقل کنیم؟

برای ریدایرکت شرطی، ادمین وارد تب Confirmation می‌شود، rule جدید می‌سازد، شرط را در IF تعریف می‌کند و در بخش THEN/Settings اکشن را روی redirect قرار می‌دهد. سپس URL صفحه مقصد را وارد می‌کند.

مثال: اگر کاربر Plan is Pro را انتخاب کرد، بعد از ارسال به صفحه رزرو جلسه منتقل شود. اگر Plan is Free بود، پیام تشکر معمولی نمایش داده شود. برای URL باید آدرس کامل و معتبر وارد شود.

## 27. چطور webhook را فقط برای بعضی فرم‌ها یا پاسخ‌ها ارسال کنیم؟

برای وبهوک شرطی، ادمین وارد تب Webhook می‌شود و rule جدید می‌سازد. در IF شرط را تعیین می‌کند؛ مثلاً Request Type is API Integration. سپس webhook ID، URL و method را وارد می‌کند.

اگر method روی POST باشد، payload کامل به URL ارسال می‌شود. اگر GET انتخاب شود، اطلاعات اصلی به صورت query به URL اضافه می‌شود. این قابلیت برای CRM، automation، helpdesk یا سیستم سفارش کاربرد دارد.

## 28. چطور چند webhook برای مسیرهای مختلف بسازیم؟

ادمین می‌تواند در تب Webhook چند rule جدا بسازد. هر rule شرط، URL و webhook ID خودش را دارد. مثال: lead فروش به CRM ارسال شود، درخواست پشتیبانی به helpdesk، و پرداخت موفق به سیستم سفارش.

برای خوانایی بهتر، هر rule باید نام واضح داشته باشد؛ مثل Send Sales Lead to CRM یا Send Support Ticket to Helpdesk. سپس با Test Mode یا submission تستی باید بررسی شود که فقط webhook مسیر درست اجرا می‌شود.

## 29. چطور قبل از انتشار فرم ruleها را تست کنیم؟

ادمین وارد Conditional Logic می‌شود و روی Test Mode کلیک می‌کند. سپس برای فیلدهای فرم مقدار نمونه وارد می‌کند و Run Test را می‌زند. نتیجه هر rule با وضعیت Matched، Not matched یا Skipped نمایش داده می‌شود.

برای فرم‌های مهم، فقط یک سناریو کافی نیست. ادمین باید مسیرهای اصلی را جداگانه تست کند: کاربر شخصی، کاربر شرکتی، درخواست فروش، درخواست پشتیبانی، بودجه کم، بودجه زیاد، پرداخت موفق و پرداخت ناموفق.

## 30. چطور تعارض بین چند rule روی یک فیلد را کنترل کنیم؟

اگر چند rule روی یک فیلد اثر می‌گذارند، ادمین باید Priority را تنظیم کند. rule با عدد کمتر زودتر اجرا می‌شود. اگر rule بعدی روی همان target match شود، می‌تواند نتیجه قبلی را تغییر دهد.

اگر ادمین می‌خواهد وقتی یک rule match شد، ruleهای بعدی همان target را تغییر ندهند، باید Stop after this rule matches را فعال کند. این گزینه فقط target همان rule را قفل می‌کند و ruleهای مربوط به فیلدها یا stepهای دیگر همچنان اجرا می‌شوند.

## 31. چطور فرم را برای کاربران شخصی و شرکتی دو مسیر متفاوت کنیم؟

ابتدا ادمین یک فیلد Customer Type با گزینه‌های Personal و Business می‌سازد. سپس فیلدهای مشترک را عادی نگه می‌دارد و فیلدهای شرکتی مثل Company Name، VAT Number یا Business Address را به صورت شرطی نمایش می‌دهد.

در Conditional Logic، برای گزینه Business اکشن‌های Show Field و Set Required ساخته می‌شود. برای گزینه Personal می‌توان Hide Field یا Set Optional ساخت. اگر فرم چندمرحله‌ای است، مرحله Company Information نیز می‌تواند فقط برای Business نمایش داده شود.

## 32. چطور فرم پشتیبانی را براساس نوع مشکل هوشمند کنیم؟

ادمین یک فیلد Issue Type می‌سازد؛ مثلاً Technical، Billing و General. سپس برای هر مسیر rule جدا تعریف می‌کند. اگر Technical انتخاب شد، فیلد Activation Code و Screenshot نمایش داده شود؛ اگر Billing انتخاب شد، Order Number required شود.

در تب Notifications نیز می‌توان برای هر نوع مشکل ایمیل جدا ساخت. Technical به تیم فنی، Billing به امور مالی، و General به پشتیبانی عمومی ارسال شود. این یکی از کاربردهای اصلی conditional logic برای کاهش کار دستی تیم پشتیبانی است.

## 33. چطور فرم درخواست قیمت را براساس بودجه شاخه‌بندی کنیم؟

ادمین یک فیلد Budget عددی می‌سازد. سپس ruleهای عددی تعریف می‌کند: اگر Budget کمتر از حداقل بود، Show Message نمایش داده شود؛ اگر Budget بین دو مقدار بود، فیلدهای مربوط به پروژه متوسط نمایش داده شود؛ اگر Budget بیشتر از مقدار مشخص بود، notification به تیم فروش ویژه ارسال شود.

برای این سناریو، operatorهای greater than، less than، between و not between کاربرد دارند. نویسنده مقاله می‌تواند مثال کامل با سه مسیر «بودجه پایین»، «بودجه متوسط» و «بودجه بالا» بسازد.

## 34. چطور فرم ثبت‌نام رویداد را براساس نوع بلیت تغییر دهیم؟

ادمین یک فیلد Ticket Type می‌سازد؛ مثلاً Free، Standard و VIP. اگر VIP انتخاب شد، فیلدهای اطلاعات مهمان یا ترجیحات ویژه نمایش داده شود. اگر Free انتخاب شد، مرحله پرداخت مخفی شود یا پیام خاصی نمایش داده شود.

اگر فرم پرداخت دارد، می‌توان شرط پرداخت موفق هم اضافه کرد. بعد از پرداخت موفق، confirmation مخصوص یا webhook ثبت سفارش اجرا شود.

## 35. چطور فرم استخدام را براساس موقعیت شغلی تغییر دهیم؟

ادمین فیلد Job Position را می‌سازد و برای هر موقعیت، فیلدهای مرتبط را نمایش می‌دهد. مثلاً برای Designer، فیلد Portfolio URL required شود؛ برای Developer، فیلد GitHub یا Technical Skills نمایش داده شود.

در تب Notifications نیز می‌توان هر موقعیت شغلی را به ایمیل مسئول همان تیم ارسال کرد. این باعث می‌شود فرم استخدام بدون ساخت چند فرم جداگانه، چند مسیر استخدامی متفاوت داشته باشد.

## 36. چطور فرم پزشکی یا intake را با سوالات وابسته بسازیم؟

ادمین سوالات پایه را می‌سازد و سپس برای پاسخ‌های حساس، سوالات تکمیلی نمایش می‌دهد. مثال: اگر کاربر پاسخ دهد که داروی خاص مصرف می‌کند، فیلد نام دارو و دوز مصرف required شود.

در چنین فرم‌هایی باید Test Mode جدی گرفته شود، چون hidden و required بودن فیلدها اهمیت زیادی دارد. بهتر است هر مسیر حساس جداگانه تست شود تا سوالات ضروری در مسیر درست نمایش داده شوند.

## 37. چطور از مقدار dataset برای پر کردن خودکار فیلد استفاده کنیم؟

اگر Auto-Populate یا Dataset فعال باشد، ادمین می‌تواند در اکشن Set Value منبع مقدار را از static به dataset column تغییر دهد. برای این کار ابتدا dataset و mappingهای لازم باید در تنظیمات Auto-Populate آماده شده باشند.

در Conditional Logic، ادمین rule را می‌سازد، در THEN اکشن Set Value را انتخاب می‌کند، target را فیلد مقصد می‌گذارد و از لیست dataset column ستون مورد نظر را انتخاب می‌کند. این برای پر کردن خودکار نام، شهر، کد مشتری یا اطلاعات داخلی مناسب است.

## 38. چطور یک فرم کوتاه‌تر برای مسیرهای ساده بسازیم؟

ادمین فرم کامل را می‌سازد، اما stepها و فیلدهای غیرضروری را با Hide Field یا Hide Step برای مسیرهای ساده مخفی می‌کند. مثلاً اگر کاربر درخواست ساده دارد، مراحل شرکت، پرداخت یا جزئیات پیشرفته نمایش داده نشوند.

این روش باعث می‌شود یک فرم واحد بتواند هم مسیر ساده داشته باشد و هم مسیر پیشرفته. نکته مهم این است که فیلدهای مخفی‌شده نباید required باقی بمانند و باید در Test Mode مسیر ساده کامل بررسی شود.

## 39. چطور با یک فرم واحد چند نوع درخواست را مدیریت کنیم؟

ادمین یک فیلد Request Type در ابتدای فرم می‌سازد؛ مثلاً Sales، Support، Partnership و Billing. سپس برای هر نوع درخواست، فیلدها، stepها، پیام‌ها، notificationها و webhookهای مناسب همان مسیر را تعریف می‌کند.

این سناریو بهترین نمونه استفاده از Conditional Logic است، چون به جای ساخت چند فرم جداگانه، یک فرم مرکزی ساخته می‌شود که رفتار آن بر اساس پاسخ کاربر تغییر می‌کند.

## 40. چطور بفهمیم چه مقاله‌هایی باید برای کاندیشنال لاجیک بنویسیم؟

از دید سرچ کاربران، مقاله‌ها باید با عبارت‌های عملی شروع شوند: «چطور فیلد را شرطی نمایش دهیم»، «چطور ایمیل را براساس پاسخ ارسال کنیم»، «چطور فرم چندمرحله‌ای را شرطی کنیم»، «چطور پیام تشکر متفاوت بسازیم»، «چطور webhook شرطی ارسال کنیم»، و «چطور ruleها را قبل از انتشار تست کنیم».

برای هر مقاله، ساختار پیشنهادی این است: سناریوی واقعی، فیلدهای لازم، مسیر ساخت rule در UI، تنظیمات IF، تنظیمات THEN، تست با Test Mode، نکات خطاهای رایج، و یک مثال آماده برای استفاده در فرم‌های واقعی.
