# Entries management (F14) — DB version 1.10

> [Docs index](../README.md) · Spec: [F14](../feature-gaps/F14-entries-management.fa.md) (§5, subtask A) · Date: 2026-11-14

`EMSFB_DB_VERSION` 1.9 → **'1.10'**. The constant is a **string** from now on: as a number, `1.10` is `1.1`,
which `version_compare()` puts before `1.9`, so the upgrade would never run. `Emsfb::maybe_upgrade_schema_efb()`
(`plugins_loaded`, priority 11) runs `Install::upgrade_schema()` once the stored `Emsfb_db_version` is lower;
activation runs it too.

| Table | Change | Target state | Action / notes |
|---|---|---|---|
| `{prefix}emsfb_msg_` | `ADD COLUMN entry_status TINYINT NOT NULL DEFAULT 0`, `starred TINYINT NOT NULL DEFAULT 0`, `trashed_at DATETIME NULL`, `edited_at DATETIME NULL`; `ADD KEY form_status_date (form_id, entry_status, date)`, `ADD KEY read_ (read_)` | `entry_status` 0 active, 1 spam, 2 trash; `starred` 0/1; `trashed_at` when it went to the trash (the trash is emptied after `trash_days`); `edited_at` the last administrator edit | **One** `ALTER TABLE` with every missing clause, so a big table is rebuilt at most once (MySQL before 8.0 copies the table for each `ALTER`; 8.0 adds these columns in place). A server that refuses a multi-clause `ALTER` gets one clause at a time. Every part is looked up first (`SHOW COLUMNS`, `SHOW INDEX`). No `UPDATE` of existing rows: the defaults are the old meaning (active, not starred). `read_` (0 new, 1 read, 2 pending payment, 3 new reply, 4 closed) is not touched |
| `{prefix}emsfb_msg_notes_` | `CREATE TABLE` (when missing) | `note_id`, `msg_id` (KEY), `user_id`, `note` (TEXT), `date` | Internal notes. Never in the response box, the tracking page or e-mails |

Data migration (once, never inside the upgrade request):

- `Install::upgrade_f14_schema()` only **schedules** the single cron event `efb_entries_stats_backfill` and stores
  the option `emsfb_stats_bf` (`max` = the last `msg_id` at the upgrade, `until` = the upgrade time, `cursor`).
- Each run counts 5,000 entries by `msg_id` (`GROUP BY form_id, DATE(date)`) into `submits`, then, once, the views
  of the days `emsfb_stts_` still holds (rows of a form page, `visit` or `send`) before `until`. It reschedules
  itself until `done`. Entries and sessions after the upgrade are counted live (`Entries::bump()`), so nothing is
  counted twice. Days before the stored sessions show "No data yet" for views.

Options:

- `emsfb_stats_bf` (autoload off): the backfill state.

Rules kept:

- One step, `Install::upgrade_f14_schema()`, after F05's and **before** the early return of `upgrade_schema()`
  (`tests/test-entries-schema.php`). The DDL lives in `\Emsfb\Entries::ddl()`; `install()` creates the tables and
  the fresh `emsfb_msg_` already has the columns and keys.
- A counter is one `INSERT IGNORE` of the day's row and one `UPDATE … SET n = n + 1` (atomic on MySQL, MariaDB and
  SQLite, the pattern of F05's stock and F11's counters), not `ON DUPLICATE KEY UPDATE`, which the SQLite layer and
  the unit-test database read differently.
- Without the new columns (an upgrade that has not run yet), the entries screen keeps the old list
  (`get_messages_id_Emsfb`) and the new actions answer "A database update is required".
- Permanent deletion (one entry, bulk, the trash, the form, retention, WordPress erasure) removes the entry's notes
  and history rows with it (`efb_entries_purged`).
- Tables are not dropped on uninstall (core rule).
